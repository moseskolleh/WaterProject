# Repair roadmap

This is the list of what is wrong with the toolkit's outputs, in the order
it will be fixed. It was built from an audit of the three worked examples
(`examples/projects/`) as regenerated by the current code: every figure was
looked at, every `.docx` was dumped and read as a client or a ministry
reviewer would read it, and every number was traced back to the code that
produced it. Eight areas were audited by independent auditors, and every
finding below was reproduced by the auditor that reported it, with a
script or by dumping the figure or document. A few findings carry an
independent second verification or a direct check by the maintainer of
this branch, and are marked as such.

Severity is about consequence, not effort:

- **C** critical: a wrong result reaches a client document or a drilling
  decision.
- **H** high: a misleading output, or two outputs of one project that
  contradict each other.
- **M** medium: a degraded or unclear output.
- **L** low: cosmetic.

Status marks: `[ ]` open, `[x]` fixed on this branch. "verified" means an
independent second auditor tried to refute the finding and could not;
"checked" means it was reproduced a second time by hand on this branch.

## Execution order

The order is by consequence first, then by dependency, then by locality:
what feeds a drilling decision goes before what describes it; the rule a
figure depends on goes before the figure; fixes in one file go together.

0. Housekeeping: orphaned example outputs, and a guard so stale outputs fail CI.
1. Depth of investigation and VES interpretation. Feeds siting, the sections, the geophysical report and the pre-drilling design.
2. Survey-scale maps and sections. The report crashes on a straight traverse; the section, the captions and the drill-target map are wrong.
3. Pumping-test hydraulics. The transmissivity, the pump depth and the "sustainable" verdict.
4. Borehole design and drawing. Screens against the wrong depths, a design captioned as-built, a pack that cannot be placed.
5. Report text and documents. Boilerplate, captions, claims and tables; the water-quality verdicts.
6. Regional cartography and bundled data. The maps at the front of every report.
7. Browser engine and Streamlit parity. Every step above carries its mirror; this step is what only the browser gets wrong.
8. Data, geodesy and parsers. Two critical parser defects (non-detects read
   as measurements; an unsigned longitude placed 250 km away with no flag)
   and the hole rings that erase dykes from the maps; ordered last only
   because the engines above must be fixed before their inputs are
   re-plumbed, and each of these is a self-contained fix that can be
   pulled forward.

Every engine change lands as Python + JavaScript mirror + tests +
regenerated example outputs + parity reference, in one commit, so the
two engines never disagree on a client document (see "Cross-cutting").

## Cross-cutting rules for every fix

- Python and JavaScript change in the same commit; then
  `python tests/webapp/make_reference.py`, `node tests/webapp/parity.mjs`,
  `python web/build_webapp_data.py` if data changed, and
  `python web/build_offline.py` last.
- A figure change changes its caption; the three examples are regenerated
  and their inputs and outputs are committed together; `build_catalogue.py`
  is regenerated in the same change.
- Flags reach the client documents: design flags, pumping-test flags and
  VES flags each get a "checks" block in the report that carries them.
- One depth-of-investigation rule, one rounding rule, one lithology class
  table, one UTM-zone rule, shared by both engines and pinned in
  `reference.json`.
- Prose that both engines write is worded once and held to parity; prose
  only one engine writes is asserted in `review.mjs`.
